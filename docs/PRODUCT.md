# 产品化说明 · 从「能跑」到「能给人用」

> 这份文档记录：原型 → 产品之间到底差了什么，以及每一刀为什么切在那里。
> 决策全文见 [`state/DECISIONS.md`](state/DECISIONS.md) 的 D-022 ~ D-026。

## 一句话结论

原型是**「在我这台机器上能跑的研究代码」**。产品是**「别人 pip install 完就能用、
长跑不会白费、出错说得清」**。中间的距离不是加个 `--help`，是五件具体的事。

---

## 一、装上就能用（D-022）

### 之前

```python
# 每个模块都有这一行
FFMPEG = '/opt/homebrew/bin/ffmpeg'
```

```python
# 每个脚本/测试都有这两行
sys.path.insert(0, str(ROOT))
from src.kf.kcenter import kcenter
```

没有 `pyproject.toml`，没有入口命令。用户拿到仓库只能：

> "你先 `python3 -m venv venv`，然后 `venv/bin/pip install numpy opencv-python-headless`，
> 然后**必须**在仓库根目录下跑 `venv/bin/python scripts/kf_extract.py`……
> 哦对了你 ffmpeg 装在 `/opt/homebrew/bin` 吗？不是的话改一下第 35 行。"

这不是产品。

### 现在

```bash
pip install kf-extract
kf-extract 视频.mp4 --k 80
```

从**任意目录**都能跑，不需要 PYTHONPATH，不需要在仓库里。

### 具体做了什么

| 改动 | 文件 |
|---|---|
| 外部程序定位（env → PATH → 平台常见位 → imageio-ffmpeg） | 新增 `procs.py` |
| 包前缀 `src.kf` → `kf`，31 处导入 | 全仓 |
| `sys.path` 指向 `src/`，13 处 | 脚本 + 测试 |
| `pyproject.toml` + `console_scripts` 入口 | 新增 |
| 版本号单一来源（`__version__`） | `pyproject.toml` 用 `attr` |

### 几个不显眼但很关键的细节

**① 找到二进制不算数，要能跑起来。**
`os.path.exists` 通过、但架构不匹配（x86 装在 ARM 上）或是个 0 字节占位文件，
一执行就报错。所以 `_runs()` 会真跑一次 `-version`。

**② 显式指定却失败时，不许静默回退。**
用户设了 `KF_FFMPEG=/my/path`，如果那个路径坏了而我们偷偷用了 PATH 里的，
用户会以为自己的配置生效了。这种情况直接报错，并说明「这个路径存在但无法执行」。

**③ 锁只包住字典读写，不包住解析过程。**
第一版把整个 `find_ffprobe` 包在 `with _LOCK:` 里，而它内部调 `find_ffmpeg`，
后者也要同一把**非可重入锁** → **自死锁**。表现是 `describe()` 永久挂起
（我第一次跑就挂在那儿，60 秒后才发现）。
修法不是换 `RLock` 掩盖问题，而是把锁的粒度缩到只保护 `_CACHE`。

**④ 降级路径必须自己说出来。**
`imageio-ffmpeg` **只带 ffmpeg，不带 ffprobe**（实测确认，找遍包目录没有）。
所以「缺 ffprobe」是一个真实会走到的分支，不是假想兜底：
时长/帧率改从 `ffmpeg -i` 的 stderr 解析（14.033s → 14.03s，差 0.003s），
并在 `warnings` 里明说「精度略低、时间戳可能有 ±1 帧偏差」。

## 二、真的拼图（D-026）

### 之前

整本 token 经济账建立在「一张 1066×600 的图装 4 帧 = 407 token，
而 4 张独立的 1920×1080 = 3872 token」之上。

但原型 `--canvas` 这个参数**只打印预算，没有一行代码真的拼图**。
用户拿到的是 80 张独立 PNG —— 那笔账从未兑现。

### 现在

```bash
kf-extract 番剧.mp4 --k 80
# → sheet-000.jpg … sheet-019.jpg，每张 4 格，共 8140 token
```

### 三个刻意的设计

**① 时间戳烧进像素，不是只写 JSON。**
模型看图时不知道 `frame-00042.png` 是第几秒。烧上 `#42 07:14` 后，
模型能引用「第 42 张、7 分 14 秒」，而用户能在 `extract.json` 的
`keys_time_sec[42]` 查到**同一个数**。两边同口径 = 产物自证。

**② 点阵字库，不用系统字体。**
系统字体在每个平台渲染不同 →「同参数同产出」的可复现性就破了。
内置 39 个 5×6 点阵字形（`0-9 # : / . - 空格 A-Z`），
并有一条测试锁死「时间戳会用到的每个字符都有字形」。

**③ 等比缩放 + 居中补黑，不拉伸。**
直接 `resize((w,h))` 会把 16:9 压成格子比例。画面变形后，
人眼判断「这两帧像不像」会失准 —— 而"像不像"正是这个工具的核心判断。
有一条测试专门验证补边而不是拉伸（检查上下是否有黑边）。

## 三、长跑不白费（D-024）

### 之前

29 分钟素材要跑 85 秒。用户在 85 秒里最容易做的事就是按 Ctrl-C。

原型的反应是：

1. 抛 `KeyboardInterrupt`，**已经跑完 40 秒的解码全丢**；
2. 已经导出的 PNG 和下一次运行的产物**混在一起**；
3. 退出码 130，但没有任何「进行到哪一步」的记录。

### 现在

| 行为 | 实现 |
|---|---|
| 阶段级原子落盘 | 每阶段进出都 `mark()` + `os.replace` 原子写 |
| 指纹失效 | 素材 `size+mtime_ns` + 全部影响该阶段的参数 → sha256 |
| 中断语义 | `SignalGuard` 把信号转成 `Interrupted(Exception)` |
| 部分结果 | 落 `status: interrupted` 的报告，保留 state |
| 退出码 | **130**，绝不打印 `PASS` |

### 实测踩到的三个坑（都已修）

**坑 1：解码阶段中断，连状态文件都没留。**
用户看到空目录，以为工具什么都没做。→ 改成任务**开始时就**落盘一次状态。

**坑 2：导帧阶段中断，收到 `subprocess.py` 的裸 traceback。**
根因：`subprocess.run` 内部的 `communicate` 抛的是 `KeyboardInterrupt`
（`BaseException`），而收尾逻辑写在 `except Exception` 里 —— **抓不到**。
这正是铁律 R282 说的事：`except Exception` 抓不到 `KeyboardInterrupt`，
所以"优雅停止"从来没运行过。
→ 三个阶段的全部包进 `SignalGuard`。

**坑 3：状态停在 `running`。**
用户不知道自己是"中断了"还是"崩了"。→ 区分 `interrupted` / `failed` 两种终态。

### 实测数字

| 项 | 值 |
|---|---|
| Ctrl-C 响应 | **0.02 秒** |
| `--resume` 后解码 | **55.8s → 0.0s** |
| 总耗时（续跑） | 101s → **45.8s** |
| 改 `--fps` 再 `--resume` | 解码缓存**失效并重算**（不会拿旧帧冒充） |

## 四、改参数不撒谎（D-025）

### 之前（一个会让下游拿到错数据的 bug）

```
kf-extract 视频 --k 40    → 目录里 40 张 png
kf-extract 视频 --k 12    → 目录里仍然是 40 张 png
```

旧文件**全部合法、能打开、编号连续**。用户以为这次抽了 40 帧。

### 根因是双重的

1. `_export_frames` 用 `glob('frame-*.png')` 收集产物 → 把上一轮的 28 张
   也算进本轮，**报告说"导出了 40 张"**；
2. 上一步让 `prune_stale` 的 `keep` 清单包含旧文件 → **永不清理**。

报告和目录**同时在撒谎**，而这两件事互相掩护、谁也看不出问题。

### 修法

- 只按 `-start_number 0` 的**连续编号**取本轮产物；
- **数量不符直接报错**（宁可失败，不许少给也不许凑数）；
- `prune_stale` 的边界：**只删自己命名规则内的**，用户文件一个不碰
  （R135：证明不了它没在用，就绝不删）。

### 实测

破坏修复 → k=12 后目录仍是 **40** 个 png（测试能红）
修复后 → **12** 个 png + 3 张拼图，`pruned` 列出 35 个被清文件

## 五、一个会静默算错的 bug（D-023）

这是产品化过程中**最危险**的发现，值得单独说。

### 现象

为保证中断续跑，新增流式解码器，它交 **uint8**（省 4× 内存）。
直接喂给 k-center 后：

| 输入 dtype | keys | maxdist |
|---|---|---|
| float32 | `[0,24,40,47,55,58,69,83]` | **13.86** |
| uint8 | `[0,24,37,43,46,48,61,68]` | **39.10** |

### 根因

```python
np.abs(np.uint8(3) - np.uint8(250))   # → 9   （真实差 247）
```

无符号减法先回绕再取绝对值。于是「差最远的帧」被算成「几乎相同」，
贪心选帧的每一步都建立在**错的距离**上。

### 为什么这是最坏的一类 bug

**不报错、不崩、结果看着完全合理。** 只有当两条路径的数字并排放才露出来。

### 修法与防复发

- `kcenter` / `kcenter_balanced` 入口统一 `_as_float()`；
- **没有**改 `metrics.pairwise_l1` —— 那是冻结口径文件，改它会让所有历史数字的
  代码路径动起来，还得重新冻结基线。入口归一化不碰数学；
- 两条测试：① 结果必须完全相同；② **元断言**：证明「uint8 会回绕」这个前提仍成立
  （如果哪天 numpy 改了语义，这条会红，提示我们重新评估）。

## 六、验收清单（都是实测的，不是声称的）

```bash
# 1. 全新环境安装
python3 -m venv /tmp/inst && /tmp/inst/bin/pip install .
cd /tmp && /tmp/inst/bin/kf-extract --version        # → 0.2.0（不是 0.0.0）

# 2. 从仓库外跑（证明不依赖仓库结构）
cd /tmp && /tmp/inst/bin/kf-extract 视频.mp4 --k 80

# 3. 无 ffmpeg 时说得清（退出码 3 + 三平台安装命令）
env -i PATH=/nonexistent KF_FFMPEG=/nope kf-extract 视频.mp4 --k 8

# 4. 全量测试
for f in tests/kf/test_*.py; do python3 $f; done    # → 124 条

# 5. 基线未动（重构不许改数学）
python3 scripts/freeze_baseline.py --check          # → ✅

# 6. 长期验证：29 分钟素材
kf-extract eval/fanren184.mp4 --k 80 --out /tmp/x    # → 85.1s, maxdist 43.4
# 中途 Ctrl-C → 退出码 130，响应 0.02s
kf-extract eval/fanren184.mp4 --k 80 --out /tmp/x --resume   # → 解码 0.0s
```

| 320 | 34.1 | 34.1 | ✅ |
