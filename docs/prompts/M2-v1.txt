## 验收（外部锚点，不接受"我测过了"）

### A4-1 · 耗时

```
bash scripts/accept_m2.sh
```

必须输出：

```
PASS: fanren184@6fps 端到端 1050s -> XXXs (要求 <= 180s)
```

**锚点**：同一个素材、同一台机器、同一条命令；改前改后各跑一次，两次都在报告里。

### A4-2 · **基线数字逐个不变**（这条最容易翻车）

改完后必须跑：

```bash
bash scripts/accept_m2.sh --baseline-check
```

它会对 **trailer 168 帧** 重算，并断言这四组数字**逐位相同**：

| 项 | 冻结值 |
|---|---|
| k-center 预算 10 | 14 |
| k-center 预算 15 | 7 |
| k-center 预算 20 | 6 |
| k-center 预算 30 | 4 |
| uniform 预算 10 | 100 |
| uniform 预算 15 | 14 |
| uniform 预算 20 | 12 |
| uniform 预算 30 | 5 |

**任何一位不同 → FAIL，不许提交。** 这不是"差不多"，是"逐位"。
（D-010 就是因为用阶梯近似，把 7.14 变成 9.0 —— 那是**换度量**，不是优化。）

### A4-3 · 内存

30 分钟素材全程 **RSS ≤ 500MB**（实测 464MB 是可行区间）。
用 `scripts/bench_m2.py --watch-rss` 报告峰值。

### 反向样本（缺一不算过）

你必须演示**两条会红的路径**，截图/输出原文贴进报告：

1. 故意把 `maxdist` 的 chunk 设成 `10**9`（等于不分块）→ 必须 OOM 或 RSS > 2GB，
   证明分块是真的在起作用（不是碰巧没炸）。
2. 故意把 `uniform` 的二分换成 7 点阶梯 → `accept_m2.sh --baseline-check` 必须 FAIL。

## 允许的技术路线（按性价比排序，可自选）

1. **降维**：32×18=576 维 → PCA/随机投影到 32–64 维，先验证「距离保序性 ≥ 95%」
   再用降维空间做 k-center。**注意**：这**会改变数字**，所以只能用于"加速候选池筛选"，
   最后仍要在原空间复算。任何改变最终数字的做法一律 FAIL。
2. **候选池 + 精算**：先按降维/粗分块选 Top-N 候选，再在原空间精确算 maxdist。
3. **uniform 的二分换成"预算→K"解析近似 + 精确复核**：只要最终 K 与原二分一致即可。
4. **多进程**：`multiprocessing` 分块并行算 maxdist（macOS 用 `spawn`，注意 pickle 成本）。

**禁止**：改判别阈值、改分块块大小导致结果变化、用 float16 造成精度漂移（会改数字）。
