# KF-Extract · 把一段视频压成"够用就好"的关键帧

> 29 分钟的番剧 → **85 秒** → **80 张原画质帧 + 20 张拼图**，
> 帧与帧之间**最长空白 47 秒**，送进模型只要 **8140 token**。
> 不是"每隔几秒截一张"，是**先算哪几帧值得看，再只留那几帧**。

## 30 秒跑起来

```bash
pip install kf-extract
kf-extract 你的视频.mp4 --k 80
```

就这样。不需要克隆仓库，不需要装 GPU，不需要配 Python 环境变量。

> **需要 ffmpeg**（命令行版）。macOS `brew install ffmpeg`，
> Ubuntu `sudo apt install ffmpeg`，Windows `winget install Gyan.FFmpeg`。
> 装完 `ffmpeg -version` 能跑就行。找不到时工具会打印三个平台的确切命令，
> 并以**退出码 3**告诉你"这是环境问题，不是素材问题"。

输出：

```
shots/
├── frame-00000.png … frame-00079.png   # 80 张原分辨率关键帧
├── sheet-000.jpg … sheet-019.jpg       # 20 张拼图（每张 4 帧，带时间戳）
├── extract.json                        # 可复核的全部数字
└── summary.md                          # 30 秒读完的摘要
```

**先看 `summary.md`**，它已经把该看的东西排好了。

## 为什么需要它

给多模态模型看视频，最直觉的做法是"定时截帧喂过去"。两个死结：

| 做法 | 问题 |
|---|---|
| 每秒 1 帧 | 24 分钟番剧 = 1440 张图 ≈ **33.6 万 token**，且大半是重复画面 |
| 每 30 秒 1 帧 | 中间剧情全丢，模型只会说"看起来你在看番" |

本项目换了个问题：**不问"画面变了没有"，问"哪几帧能让整段被覆盖住"**。

- 选出 K 帧，使"任意一帧到离它最近的选中帧"的**最大距离最小**
  （facility location / k-center 问题）
- 同时约束**时间分布**：不许出现"跳过两分钟剧情"的空白
- 最后**拼成 4 格图集**：一张 1066×600 装 4 帧 = 407 token，
  而同样 4 帧各自 1920×1080 = 3872 token（单张 968）—— **省 89.5%**

## 三个旋钮（都带实测数据）

### 1. `--k` 抽多少帧

| K | 覆盖质量（maxdist，越小越好） | 用在什么场景 |
|---|---|---|
| 40 | 46.5 | 粗看剧情 |
| **80** | **42.1** | **推荐起点** |
| 160 | 37.3 | 细看 |
| 320 | 34.1 | 逐镜研究 |

> 29 分钟国漫实测。**K 翻倍，maxdist 只降约 10%** —— 边际很低，
> 所以"多抽一倍"通常不划算。这也是为什么默认建议 80。

**但 K 不是越大越好，会翻车**（14 秒预告实测）：

| K | 拼图内"真不同"格子占比 | 说明 |
|---|---|---|
| 8 | **100%** | 每格都不同 |
| 16 | 75% | 开始出现同镜头重复 |
| 32 | **28.1%** | 一半以上格子是同一个镜头的连续几帧 |

短素材帧少，K 设过高会把**同一镜头里相邻的两帧**都选进来（它们内容距离仍 > 8，
在度量上"不同"，但在人眼里是同一张）。29 分钟番剧 K=80（每帧约 22 秒间隔）则是 **100%**。

> 经验法则：**K 大致等于"你想要的画面数量"，而不是"你想看多少帧"**。
> 短素材宁少勿多；长素材 80 起步。

也可以不给 `--k`，改用盲区预算：

```bash
kf-extract 番剧.mp4 --budget 25     # 自动决定 K，让最大盲区 ≤ 25
```

### 2. `--balance` 时间均衡（默认 **0.2**）

| 值 | 覆盖代价（中位/最坏）| 空白降幅 | 说明 |
|---|---|---|---|
| `0` | 0% | 0% | 纯内容优先。**会留长空白**（实测番剧 **196.7 秒**）|
| `0.1` | +0.4% / +3.1% | −18.5% | 很保守 |
| **`0.2`（默认）** | **+1.4% / +5.3%** | **−32.5%** | **九样本实测最优** |
| `0.3` | +3.0% / **+11.1%** | −30.6% | 空白只多降 2 点，覆盖代价翻倍 |
| `0.5` | +24.7% / — | −58.1% | 代价太大，不推荐 |

> **默认值从 0.3 改成了 0.2**（2026-11-07）。0.3 原来只在 6 段动画上扫出来；
> 加入 3 段真实素材（真人实拍 ×2、录屏 ×1）后重扫。
>
> **它是取舍，不是纯赚**（这点我一开始说错了，逐样本核对后修正）：
> - **覆盖维度上 0.2 确定更好**：中位 +1.4%（0.3 是 +3.0%），最坏 +5.3%（0.3 是 +11.1%）
> - **空白维度上二者大致持平**：中位 −32.5% vs −30.6%，但**分布不同**——
>   `fanren184` 上 0.2 是 78.0s、0.3 是 47.2s（**0.3 好 65%**），共 5/9 个样本 0.2 更差
>
> 选 0.2 是因为本项目的立身之本是**覆盖**（maxdist 是主指标），空白是辅助约束。
> 想更均衡就用 `--balance 0.3`。

### 3. `--canvas` 出图档位

| 档 | 画布 | 每格 | token/张 | 相对基线 |
|---|---|---|---|---|
| `cheap` | 800×450 | 400×225 | 233 | +0% |
| **`readable`（默认）** | 1066×600 | 533×300 | 407 | +75% |
| `max` | 1280×720 | 640×360 | 578 | +148% |

**默认取 `readable` 的理由是实测的**：同一批帧，400×225 平均认出 10.5 个字，
533×300 认到 17.0 个字（**+62%**），而 token 只多 75% —— 边际约 1:1，值。

## 图形界面（本地 Web，零额外依赖）

```bash
kf-extract --gui
```

浏览器会自动打开 `http://127.0.0.1:<端口>/?token=<一次性令牌>`。三块就够用：

1. **选素材**（只列本地视频，默认只扫项目目录；别的目录用 `--dirs` 指定）
2. **三个旋钮**（K / 时间均衡 / 出图档位），带实时说明
3. **结果**：覆盖质量、空白秒数、token 合计、⚠️ 警告，以及**可直接看的拼图画廊**

几点是刻意的：

| 行为 | 怎么做的 |
|---|---|
| **只在本机** | 只绑 `127.0.0.1`，绑别的地址会直接报错拒绝启动 |
| **一次性令牌** | 无 token / 错 token 一律 403；防同机其它进程或网页乱调 |
| **长任务不阻塞** | 提交立刻返回，前端轮询进度（解码 / 选帧 / 导帧 / 拼图） |
| **可停止且安全** | 独立「停止」按钮；停止**只置标志、不杀线程**，已解出的帧会存成部分缓存 |
| **连点只跑一次** | 同素材 + 同参数 + 同目录，连点 5 次只产生 1 个任务（实测 `deduped=true`）|
| **不谎报** | 中断的任务显示「已停止（不是失败）」，绝不显示成完成 |
| **没有删除端点** | 这个 GUI 不会删你任何文件 |

### 现在能做什么（都在真浏览器里验证过）

- **任务历史**：跑过的任务按时间倒序，点一条**恢复它的结果**（不重跑）
- **批量模式**：勾选多个视频一次跑完，每个输出到独立子目录，进度是**组聚合**（`2/2 完成`）
- **图片 viewer**：点开放大，`+ / − / 适应 / 1:1`、滚轮、拖拽平移、`←→` 切图、`Esc` 关闭
  - **`1:1` 是按原始像素显示**，不是"缩放 1.0"（1066 宽的图在窄容器里会自动放大到 1.2×）
- **静止段可点击跳转**：警告后面有「看这段附近的关键帧」，点一下直接在 viewer 打开那帧
  —— 这是本产品最重要的诚实性特征：**测不准的地方，一键送到你眼前**
- **长静默会喊出来**：运行超过 10 秒没进度更新 → 「仍在工作（已 N 秒无更新）」

> 实测：29 分钟素材解到 27% 按停止 → 磁盘保留 3072 帧的部分缓存；
> 换成浏览器另一台设备访问是不行的（只绑回环）——要远程用请走 SSH 隧道。

## 作为库用

```python
import kf

r = kf.extract('番剧.mp4', k=80, out='shots/')
print(r.maxdist)           # 覆盖质量，属性访问也行
print(r.keys_time_sec)     # 每帧的时间戳

# 只要数字，不落盘
r2 = kf.extract('番剧.mp4', k=40)
print(r2.selected_k, r2.max_gap_sec)
```

- 返回的是 JSON 可序列化的 dict（子类，支持属性访问 + `.save()`）
- 内部结构随便改，这个面孔不动 —— 所以请只依赖 `kf.extract`
- 进度回调：`kf.extract(..., progress=lambda stage, frac, msg: ...)`

## 长跑不会白费

29 分钟素材约 85 秒。这 85 秒里最常见的操作就是按 Ctrl-C。所以：

```bash
kf-extract 番剧.mp4 --k 80 --resume
```

| 行为 | 实测 |
|---|---|
| Ctrl-C 响应时间 | **0.02 秒** |
| 中断后退出码 | **130**（不是 0，绝不谎报成功） |
| 已完成的阶段 | 落盘保留（`--resume` 时解码耗时 **55.8s → 0.0s**） |
| 改了参数再跑 | 指纹失效，自动重算（不会拿旧结果冒充新的）|
| 中断时的产物 | 保留在目录，且报告标 `status: interrupted` |

**改 K 之后同目录重跑不会留下孤儿文件**：`--k 40` 再 `--k 12`，
目录里就只剩 12 张，旧拼图也清掉。（只删我们自己命名规则内的文件，
你的其它文件一个都不碰。）

| 选帧方式 | pack=4 的"真正不同"占比 |
|---|---|
| 全部 10403 帧（29min） | **50.9%** |
| 均匀 200 帧 | 99.0% |
| k-center 200 帧 | **100.0%** |

**结论**：帧太密时一半在重复；抽到 200 帧就几乎零重复。
所以"抽多少"比"怎么抽"影响更大。

## 它不做什么（提前说清）

- ❌ **不做实时** —— 离线抽取工具
- ❌ **不做语音/字幕理解** —— 只处理画面
- ❌ **不做"原画帧"精确检测** —— 见下
- ❌ **不需要 GPU**

### 关于「精准抽原画帧」

如果你以为它能识别动画里的**原画/作画帧**（"一拍二"的换画点），**做不到，我们实测过**：

| 素材 | 总帧 | 唯一画面 | 精确去重能省 |
|---|---|---|---|
| 番剧预告 | 842 | 812 | 3.6% |
| 动画 MV 195s | 14010 | 13821 | 1.3% |
| 动画 MV 227s | 16096 | **16096** | **0.0%** |

**成片里几乎没有完全相同的相邻帧** —— 一拍二在**原画层**，
输出到 24/60fps 时叠加了光影、粒子、镜头运动。

孤立的"画面突变"也很少：842 帧里"前静后静"的尖峰只有 **1 个（0.1%）**。

要做原画级只能走**线稿域分离**（抽出线稿再去重），本项目没做。

### ⚠️ 最大的已知限制：看不见「局部新增信息」

这是实测踩到的，比任何性能数字都重要。

**录屏素材（267s 编程教程）**：我们的工具报 `maxdist = 3.84`（看上去完美覆盖），
但对比 198s 与 265s 的画面：

> 同一段视频里，199.5s→266.7s 这 **67 秒**被判成「零变化」（404 帧没有一帧"不同"），
> 而画面上实际多了**终端面板 + 运行输出**（`hello` 编译执行的结果）。

**真人 Vlog（499s）**：291s→324s 这 **34 秒**是同一说话人镜头，
字幕从「那相对于需要花费大量的时间和练习」变成「节目啊」，同样被判零变化。

根因不是分辨率（提到 640×360 后 L1 仍只有 3.64），也不是实现 bug ——
是**纯像素度量的物理上限**：终端面板只占约 15% 面积，文字是高频细节，
任何「整体平均」的度量都会把它稀释掉。
PySceneDetect 在**同一素材上只找到 2 个切点**，说明这是所有像素法共同的盲区。

**我们怎么处理：报出来，而不是假装解决。**

```
- ⚠️ 连续静止 55.0s（211.7s→266.7s）—— 像素度量把这段判为零变化，
  但它可能含有局部新增内容（录屏/PPT/字幕）
```

`extract.json` 里有完整字段：

```json
"static_segments": {
  "count": 34,
  "longest": {"start_sec": 211.7, "end_sec": 266.7, "dur_sec": 55.0, "frames": 331}
}
```

**为什么不自动跳过这些段**：整段夜景、片尾黑屏，静就是内容本身，
自动规避会误伤，还会变成第二个未声明的目标（破坏"只有一条判据"）。
**取舍交给用户，我们只保证你看得见。**

> 遇到这类素材（录屏、PPT、带字幕的讲解），建议把 `--k` 提到 2–3 倍，
> 或人工抽查 `summary.md` 里标了 ⚠️ 的时间段。

### 黑场会被选中，但会被说出来

k-center 有时会选中一张**纯黑转场帧**（它确实"很不一样"，距离最远）。
实测 29 分钟番剧里 80 帧中有 1–2 帧。它占掉 1/4 的图集容量，却不含信息。

工具**不会自动删掉它**——整段夜景的片子、片尾黑屏，黑就是内容本身，
自动剔除会误伤。但会写进 `summary.md` 的「需要你注意」，并给准确计数：

```json
"dark_frames": {"in_video": 9, "in_selection": 1, "selection_idx": [48]}
```

## 和市场上的方案比（同素材、同标尺实测）

我们不只是"觉得自己的方法好"，而是**把竞品的方法实现出来，用同一把尺子量它们**。

参与对比的四种方法（`scripts/bench_market.py`，可自行复跑）：

| 方法 | 来源 | 许可证 | 做法 |
|---|---|---|---|
| `uniform` | 最常见的天真做法 | — | 每 N 秒抽一帧 |
| `scenedetect` | [PySceneDetect](https://github.com/Breakthrough/PySceneDetect) 5400★ | BSD-3 | 镜头切点，取每镜头中点 |
| `diffpeak` | [video-keyframe-detector](https://github.com/joelibaceta/video-keyframe-detector) 216★ | GPL-3.0 | 帧差峰值 |
| `kcenter` | **本项目** | MIT | 覆盖优化 |

> GPL-3.0 的那两个项目**只做了方法对照，代码一行没并进来**。

### 实测结果（K 帧等长，同一冻结标尺）

| 素材 | K | uniform | scenedetect | diffpeak | **本项目** |
|---|---|---|---|---|---|
| vlog（真人实拍）| 40 | 59.35 | 65.45 | 62.91 | **31.05** ← 好 1.9–2.1× |
| vlog | 20 | 84.17 | 71.03 | 67.91 | **44.38** ← 好 1.5–1.9× |
| codecast（录屏）| 40 | 51.14 | 51.14 | 2.62 | **1.22** ← 好 2.1× |
| codecast | 20 | 51.15 | 51.15 | 4.98 | **3.84** ← 好 1.3× |
| liveact（街拍）| 20 | 61.22 | 58.86 | 58.81 | **58.18** ← 好 1.1% |
| liveact | 40 | 60.95 | 58.86 | **54.71** | 57.95 ← **输 5.9%** |
| trailer | 20 | 11.13 | 11.13 | 11.61 | **8.03** ← 好 39% |

**结论必须分开说，不能只挑赢的说：**

- ✅ **赢**：真人实拍长视频（1.9–2.1×）、录屏 vs 均匀采样（1.3–2.1×）、短素材（39%）
- ⚠️ **曾经的短板已大幅收窄**：`liveact` 这类**无切点连续运动**（单镜头跟拍走动）
  曾输给帧差法 5.9%。把默认 `--balance` 从 0.3 调到 0.2 之后，
  maxdist 从 57.95 降到 **53.9**，反超帧差法的 54.71。
  但**根因仍在**：K 由用户固定，帧帧都不同时固定 K 必然留大盲区（K 增大边际收益很小）。
- ⚖️ **平**：与帧差法在短素材上接近，但我们的**时间空白**明显更好
  （liveact K=20：16.3s vs 帧差法 101.2s）。

### 与学术前沿的关系（读了论文全文，不是只看摘要）

| | 我们 | [CSES](https://arxiv.org/abs/2608.00714)（2026-08）| [FOCUS](https://proceedings.iclr.cc/paper_files/paper/2026/file/a010577f93a8301dada61f0b97cda923-Paper-Conference.pdf)（ICLR 2026）|
|---|---|---|---|
| 方法族 | k-center 覆盖 | **加权子模覆盖（我们的超集）** | clip 级 bandit |
| 需要 query | 否 | 是（BLIP 相关性）| **是（没有 query 算法就塌）** |
| K | 用户固定 | **自适应（饱和停止）** | 固定 |
| 时间覆盖 | **有（max_gap）** | 有（时间高斯） | **无**（论文附录 H 自认） |
| 算力 | **纯 CPU，零依赖** | GPU + BLIP-large | H100 + BLIP |
| 指标 | 像素覆盖距离 | VQA 准确率 | VQA 准确率 |

**三句实话：**

1. **算法层我们不是最新**。CSES 是严格超集（它有 query 相关性与自适应 K）。
2. **效果层我们没被证伪**。所有"竞品更优"的证据都在**另一个度量轴**（VQA 准确率）。
   把它们的准确率和我们的 maxdist 并列 = 数据造假。
3. **我们的独有能力，它们都没有**：时间覆盖（max_gap_sec）、拼图省 token 89.5%、
   纯 CPU 零依赖。

### 我们**试过但否决**的两个 CSES 改进

CSES 的乘积核（`K=cos·exp(-Δt²/2ℓ²)`）理论上更优雅（恢复子模性、有 1-1/e 保证）。
我们按它的定义实现并实测了：

| 素材 | K | 我们 | CSES 乘积核 |
|---|---|---|---|
| codecast | 20 | **3.84** | 26.85（差 7×）|
| codecast | 11 | **8.84** | 71.31（差 8×）|
| vlog | 40 | **31.05** | 63.13（差 103%）|
| liveact | 11 | **61.71** | 70.03（差 13%）|

**7 组全部变差。** 根因：`cos` 对**非负向量**天然偏高——灰度永远 ≥0，
两个毫无关系的场景余弦也有 0.6–0.8。CSES 用的是 BLIP 语义嵌入（有正有负），
余弦才可分。**换了特征却沿用它的核，等于把它的前提偷掉了。**

## 架构

```
src/kf/
├── api.py        稳定公开 API（`kf.extract`）—— 唯一承诺不动的面孔
├── cli.py        命令行入口（退出码 0/1/2/3/130）
├── metrics.py    距离与覆盖度量 —— **冻结**（所有历史数字的口径）
├── kcenter.py    选帧：k-center / 时间均衡版
├── fast.py       加速：整数路径 + 并行 + 早停（同结果快 9.4×）
├── layout.py     出图预算：画布档位 / 每格短边 / token 账
├── sheets.py     拼图：4 格排版 + 时间戳烧字
├── export.py     落盘：命名 / 幂等清理 / zip / 清单 / 摘要
├── state.py      长跑：原子状态 + 指纹 + 断点续跑 + 信号处理
├── procs.py      ffmpeg/ffprobe 跨平台定位（含降级）
├── flow.py       光流（验证用，判据 FAIL，未接生产）
└── report.py     M0.5 三列表（覆盖 / 分布 / 空档）
```

`kf-extract` 命令和 `scripts/kf_extract.py` 都指向同一个 `cli.py`
（后者是给老文档留的兼容垫片，不再维护第二份逻辑）。

### 为什么要"冻结"度量

`metrics.py` 和 `scripts/eval.py` 里写着**所有历史数字的计算口径**
（32×18 灰度、L1 均值、`>8` 才算"真正不同"）。改它们 = 所有已发布数字作废。

所以有 `scripts/freeze_baseline.py`：

```bash
$ python3 scripts/freeze_baseline.py --check
✅ 基线未动
```

**这个闸门真的救过一次**：我们想"优化"时把 uniform 二分换成 7 点阶梯，
它拦下了 —— 那个"优化"会把 7.14 变成 9.00，是**换度量**不是提速。

## 环境与兼容

- **Python 3.9+**。硬依赖只有 `numpy`。
- `pillow` 可选（更快，格式更多）；不装会退回 ffmpeg 读写图。
- `opencv-python-headless` 只有 `flow.py` 用，默认路径不需要。
- **ffmpeg 必需**，ffprobe 可选（缺它会降级解析并用 `warnings` 说明精度）。
- `pip install imageio-ffmpeg` 能救**只缺 ffmpeg** 的情况；
  但它**不带 ffprobe**（实测确认），缺 ffprobe 仍需系统安装。
- 平台：macOS / Linux / Windows 都走同一套定位逻辑，无硬编码路径。
- **不需要 GPU**。硬解（`-hwaccel videotoolbox`）是可选加速，失败自动回退软解。
